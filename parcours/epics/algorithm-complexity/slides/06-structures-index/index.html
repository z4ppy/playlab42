Structures d'Index

Comment les bases de données trouvent vos infos en 1 ms : Hash vs B-Trees.

⚡ Tables de Hachage (Hash Tables)

O(1)

Moyenne

La structure reine pour la recherche exacte.

Forces

  • Vitesse imbattable (accès direct).
  • Idéal pour les caches (Redis) et maps.

Faiblesses

  • Pire cas O(n) (collisions).
  • Ne supporte pas les intervalles ("trouver les prix > 100€").

🌲 B-Trees et B+ Trees

O(log n)

Garanti

L'épine dorsale des SGBD (PostgreSQL, MySQL, Oracle). Des arbres larges optimisés pour réduire les accès disque (I/O).

Le calcul magique :

Avec des pages de 4KB, des clés de 8 octets et des pointeurs de 8 octets, un nœud peut avoir jusqu'à 256 enfants ($t=256$).
Capacité avec hauteur 4 : $256^4 \approx 4 \text{ Milliards}$.

Conséquence : Pour trouver une donnée parmi 1 Milliard, il ne faut que 4 lectures disque.

Hauteur h $\le \log_t \frac{n+1}{2}$

Plus $t$ (degré) est grand, moins l'arbre est profond.

🤔 Le mystère du B

Les B-Trees ont été inventés en 1971 par Rudolf Bayer et Edward McCreight chez Boeing.

Mais que signifie le "B" ? Bayer et McCreight n'ont jamais donné la réponse officielle. Les hypothèses incluent : Boeing (leur employeur), Bayer (le créateur), ou Balanced (équilibré). Douglas Comer a écrit : "Plus vous y réfléchissez, plus le mystère s'épaissit".

⚖️ Comparatif : Quand utiliser quoi ?

Opération Hash Index (ex: Redis, Map) B-Tree Index (ex: SQL, Mongo)
Recherche exacte (=) O(1) O(log n)
Intervalle (>, <) Impossible (O(n)) O(log n + k)
Tri (ORDER BY) Non Naturel (Déjà trié)
Préfixe (LIKE 'abc%') Non Oui (Optimisé)

Règle d'or : Utilisez Hash pour les caches et lookups exacts en RAM. Utilisez B-Tree pour tout ce qui nécessite requêtes complexes, tris ou persistence disque.

💾 Bases de Données & Indexing Avancé

1. Index Composites & "Leftmost Prefix"

Un index composite Index(Nom, Prenom) ne crée pas deux arbres. C'est un seul B-Tree trié par Nom, puis par Prénom (comme un annuaire papier).

✅ Query: Nom = "Doe"

Le B-Tree est trié par Nom. On trouve "Doe" directement.

O(log n)

❌ Query: Prenom = "John"

L'annuaire n'est pas trié par Prénom. "John" est partout. Il faut tout lire.

O(n) - Full Index Scan

2. Recherche Multi-Index (Intersection)

Si vous avez Index(Age) et Index(Ville) séparément pour la requête Age=25 AND Ville='Paris' :

  • Naïf : La DB choisit le meilleur index (ex: Ville), puis filtre le reste ligne par ligne.
  • Index Merge : La DB scanne les deux index séparément et calcule l'intersection des IDs en mémoire.
Coût = O(log n + k1) + O(log n + k2) + O(intersection)

Plus lent qu'un Index Composite targeté $O(\log n)$.

3. Calculer la complexité SQL (Explain Plan)

Le planificateur ne calcule pas des "O(n)", il estime un Coût (I/O disque + CPU). Voici comment traduire un EXPLAIN :

Opération EXPLAIN Complexité Pourquoi ?
Index Seek / Unique O(log n) Descente d'arbre directe.
Index Range Scan O(log n + k) Trouve le début, puis lit k éléments.
Full Table Scan O(n) Lecture intégrale du disque. Lenteur guarantie.
Nested Loop Join O(N * log M) Pour chaque ligne de A, cherche dans l'index de B.
