Étape 6 · Bonnes pratiques

Bonnes pratiques et pièges à éviter

Quelques habitudes rendent le workflow fluide, illustrées sur le même fil rouge : le change add-dark-mode.

Pratiques qui paient

Explorer quand le plan manque

/opsx:explore est dans le profil par défaut. Utilisez-le quand vous avez un problème mais pas encore de plan ; il n'écrit rien tant que vous ne le demandez pas.

Un nom de change précis

Kebab-case, verbe d'abord : add-dark-mode, pas update, wip ni changes.

Des tâches petites et vérifiables

Une tâche = une responsabilité, testable. Test mental : un autre développeur pourrait-il la faire sans contexte supplémentaire ?

Des specs honnêtes

Avant d'archiver, les deltas décrivent ce que le code fait vraiment : ils deviennent la source de vérité.

Le schéma spec-driven

Schéma par défaut : les artefacts forment un graphe de dépendances. Les dépendances disent ce qui est possible, pas ce qui est obligatoire.

proposal ──► specs ──┐
        └──► design ─┴──► tasks ──► apply
ArtefactRôle pour add-dark-mode
proposal.mdPourquoi et quoi : intention, périmètre, approche
specs/ui/spec.mdDelta : exigences et scénarios (ADDED/MODIFIED/REMOVED)
design.mdDécisions : variables CSS, stockage de la préférence
tasks.mdChecklist d'implémentation numérotée

Configurer openspec/config.yaml

Le moyen le plus simple d'adapter OpenSpec à votre équipe : schéma par défaut, contexte injecté dans tous les artefacts, règles par artefact et conseils pour apply et archive.

Exemple illustratif, générique : ne le copiez pas. Dans Playlab42, ouvrez le vrai fichier openspec/config.yaml : il référence AGENTS.md et le guide docs/guides/openspec-workflow.md comme source commune de la stack et des conventions.

schema: spec-driven

context: |
  Application web statique, JavaScript sans framework.
  Tests : Jest. Interface en français.

rules:
  specs:
    - Utiliser le format Given/When/Then
  proposal:
    - Inclure un plan de retour arrière

operations:
  apply:
    guidance:
      - Lancer les tests ciblés avant la suite complète

Le context est injecté dans tous les artefacts ; les rules seulement dans l'artefact visé. Restez concis : ce texte accompagne chaque requête de planification. L'ordre de résolution du schéma est : option --schema, métadonnées du change, config.yaml, puis spec-driven.

Adopter OpenSpec sur un projet existant

Inutile de spécifier tout le code : on écrit les specs de ce que l'on s'apprête à modifier, et elles s'accumulent change après change grâce aux deltas.

openspec init            # dans un dépôt existant sans OpenSpec, crée openspec/

Playlab42 est déjà initialisé : n'y relancez pas init.

  1. /opsx:explore : faire lire à l'assistant la zone concernée.
  2. /opsx:propose sur un petit changement réel dont vous avez besoin.
  3. /opsx:apply, puis /opsx:archive : la spec de cette zone existe désormais.

Vos documents existants (PRD, etc.) servent de matière première pour l'exploration, pas de specs à convertir en bloc. Pour un tour guidé sur votre code, /opsx:onboard existe, mais seulement dans le profil expanded.

Quelle commande pour quel profil ?

ProfilCommandes d'assistant (docs v1.14.0)
core (défaut)explore, propose, apply, update, sync, archive
Expanded (openspec config profile puis openspec update)en plus : new, continue, ff, verify, bulk-archive, onboard

Le profil core compte six commandes dans la doc v1.14.0 (le README de la branche main peut en annoncer moins). /opsx:update (chat, révise le plan, jamais le code) est distinct de openspec update (terminal, régénère les intégrations).

/opsx:propose est le nom canonique. Cursor et GitHub Copilot (IDE) enregistrent /opsx-propose ; Codex $openspec-propose. Selon la documentation OpenSpec, Copilot CLI ne charge pas directement les prompts .github/prompts/*.prompt.md générés pour les extensions IDE. Vérifiez toujours quelles intégrations votre outil prend en charge.

Dans Playlab42 (politique du projet) : profil core en livraison skills seuls. Demandez le skill par son nom canonique : openspec-explore, openspec-propose, openspec-apply-change, openspec-update-change, openspec-sync-specs, openspec-archive-change. Les sources vivent dans .github/skills/ ; .claude/skills n'en est qu'un lien. Le CLI 1.14.0 est épinglé et s'exécute dans Docker :

make openspec-list
make openspec-validate
make npm CMD="exec -- openspec status --change add-dark-mode --json"
Approfondir : instructions legacy (/openspec:*) et migration

Les commandes /openspec:proposal, /openspec:apply et /openspec:archive sont l'ancien workflow ; elles fonctionnent encore mais OPSX est recommandé. Procédure officielle générale de migration d'un projet qui les utilise :

  1. Mettre à jour la CLI, puis lancer openspec init ou openspec update : les fichiers legacy sont détectés et un nettoyage est proposé.
  2. Les anciens fichiers de commandes, openspec/AGENTS.md et les blocs de marqueurs OpenSpec dans CLAUDE.md/AGENTS.md sont retirés ; votre contenu reste.
  3. Déplacer le contexte utile de openspec/project.md vers le champ context de openspec/config.yaml, puis supprimer project.md vous-même.
  4. Changes actifs, archives et specs principales sont conservés.

Dans Playlab42, ce n'est pas à rejouer : le dépôt applique déjà OPSX core en skills seuls. Les trois alias Claude /openspec:proposal, /openspec:apply et /openspec:archive sont conservés comme alias locaux de compatibilité. Le guide du projet interdit openspec init --force et openspec update directement dans le dépôt, pour préserver ces alias et instructions ; le rafraîchissement des intégrations est fait par le mainteneur dans un projet temporaire isolé, selon docs/guides/openspec-workflow.md.

Pièges fréquents

  • Sur-spécifier : une demi-page suffit pour un petit changement.
  • Dévier du plan sans mettre à jour tasks.md, design.md ou le delta.
  • Confondre openspec validate (structure), /opsx:verify (code vs artefacts) et les tests (comportement à l'exécution).
  • Recommander une commande absente du profil de l'équipe.
  • Croire qu'archiver déploie.
