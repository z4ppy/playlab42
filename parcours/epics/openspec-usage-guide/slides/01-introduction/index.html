Les bases

Specs, artefacts et installation

Dans OpenSpec, les specs décrivent le comportement actuel du système ; chaque changement vit dans son propre dossier jusqu'à son archivage.

Le développement piloté par les specs

Avec un assistant IA, un besoin resté dans l'historique de chat est vite oublié ou mal interprété. OpenSpec le fixe dans des fichiers Markdown versionnés, relus par des humains avant le code.

openspec/specs/

La source de vérité : comportement actuel, organisé par domaine (portal/, theme/…).

openspec/changes/

Les modifications proposées : un dossier par changement, avec ses artefacts et ses deltas.

Les artefacts d'un changement

openspec/changes/add-dark-mode/
├── proposal.md          # pourquoi et quoi
├── specs/
│   └── ui/spec.md       # delta specs : ce qui change
├── design.md            # comment
└── tasks.md             # checklist d'implémentation
ArtefactRôle
proposal.mdIntention, périmètre, approche
specs/ (deltas)Exigences ADDED / MODIFIED / REMOVED avec scénarios
design.mdChoix techniques et compromis
tasks.mdTâches à cocher pendant l'implémentation

À l'archivage, les deltas sont fusionnés dans openspec/specs/ et le dossier du changement est déplacé dans openspec/changes/archive/.

Installer et initialiser (projet générique)

OpenSpec exige Node.js 20.19.0 ou plus. Les commandes ci-dessous valent pour un autre projet : ne les exécutez pas dans Playlab42 (voir plus bas).

Dans Playlab42, Node.js, npm et OpenSpec s'exécutent uniquement dans Docker (make), jamais sur l'hôte.

node --version                              # >= 20.19.0
npm install -g @fission-ai/openspec@latest
cd mon-projet
openspec init

openspec init crée openspec/ et génère, pour les outils choisis, les skills et/ou commandes lus par l'assistant. Par défaut : profil core, livraison both. Après une mise à jour du CLI, openspec update régénère ces fichiers selon votre profil (core par défaut). 

openspec init --tools claude,cursor   # non interactif
openspec update                       # après mise à jour du CLI
openspec config profile               # choisir les workflows

Deux endroits, deux types de commandes

Terminal

CLI openspec

init, update, list, show, validate, view…

Chat de l'assistant

Commandes /opsx:*

/opsx:propose, /opsx:apply… Elles ne fonctionnent pas dans un terminal.

La forme exacte dépend de l'outil : /opsx:propose (Claude Code, Gemini CLI), /opsx-propose (Cursor, GitHub Copilot dans l'IDE), $openspec-propose (Codex). Les prompts Copilot .github/prompts ne sont pas pris en charge par Copilot CLI.

Concrètement dans Playlab42

Chat de l'assistant

Demander un skill

Citez-le par son nom : openspec-explore, openspec-propose, openspec-apply-change, openspec-update-change, openspec-sync-specs, openspec-archive-change.

Terminal (Docker)

CLI via make

Jamais de npm ni de node sur le host : tout passe par make.

Chat de l'assistant 
Utilise le skill openspec-propose pour créer le changement add-dark-mode
make openspec-list
make openspec-validate
make npm CMD="exec -- openspec --version"
make npm CMD="exec -- openspec list --specs"

Dans Playlab42 : déjà en place

Le dépôt est sur le workflow actuel : schéma spec-driven dans openspec/config.yaml, CLI @fission-ai/openspec 1.14.0 en devDependency locale épinglée (Node 26 dans Docker) et skills du profil core déjà générés dans .github/skills/openspec-* (.claude/skills est un lien vers ce dossier). Pas d'installation globale à faire.

La livraison est skills-only : les commandes /opsx:* ne sont pas disponibles automatiquement. Les trois alias /openspec:proposal|apply|archive de .claude/commands/openspec/ sont de simples alias locaux de compatibilité.

N'exécutez pas openspec init --force ni openspec update directement dans le worktree : ils supprimeraient ces alias et openspec/AGENTS.md. Le rafraîchissement des skills est une procédure de mainteneur, dans un projet temporaire isolé (voir le guide OpenSpec de Playlab42).
