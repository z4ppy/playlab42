Implémenter avec /opsx:apply

Le change est prêt (proposal.md, deltas de specs, design.md, tasks.md). /opsx:apply demande à l'assistant de dérouler tasks.md ; c'est vous qui relisez, corrigez le plan et décidez quand c'est fini.

Fil rouge de cette slide : le change add-dark-mode.

Lancer l'implémentation

Dans le chat de l'assistant

/opsx:apply add-dark-mode

Le nom du change est optionnel : il est déduit du contexte, mais le préciser évite toute ambiguïté si plusieurs changes sont actifs.

profil core

Selon votre outil

Dans la documentation OpenSpec, le nom canonique est /opsx:apply. Cursor et GitHub Copilot (extensions IDE) enregistrent /opsx-apply ; Codex utilise le préfixe $. Ces noms ne valent que si l'intégration a généré ces commandes.

Dans le dépôt Playlab42

Le dépôt utilise le profil core en livraison skills seuls (.github/skills/, exposé à Claude par le lien .claude/skills). Ce lien ne crée pas de commande /opsx:* : demandez à l'assistant d'utiliser le skill par son nom canonique.

Utilise le skill openspec-apply-change pour add-dark-mode

Politique du projet, pas fonctionnement général d'OpenSpec. Les trois alias Claude /openspec:* restent seulement des alias locaux de compatibilité.

Ce que fait apply : il lit tasks.md, repère les tâches non cochées, les traite une par une (code, fichiers, tests), puis coche [x]. Il peut reprendre là où il s'était arrêté : l'avancement est dans les cases à cocher.

Une tâche, une boucle avec revue humaine

  1. Lire : l'assistant prend la prochaine tâche de tasks.md, avec les specs et le design en contexte.
  2. Coder : il modifie les fichiers concernés.
  3. Vérifier : il (ou vous) lance les tests et le linter du projet.
  4. Relire : vous examinez le diff. L'IA propose, l'humain valide.
  5. Cocher : la case passe à [x] seulement quand la tâche est réellement terminée.

Exemple : tasks.md en cours

# Tasks

## 1. Infrastructure du thème
- [x] 1.1 Définir les variables CSS clair/sombre
- [x] 1.2 Détecter la préférence système (prefers-color-scheme)
- [ ] 1.3 Persister le choix de l'utilisateur   ← en cours

## 2. Interface
- [ ] 2.1 Ajouter le bouton de bascule
- [ ] 2.2 Vérifier les contrastes en mode sombre

Quand le plan ne tient plus : boucles de retour

Il n'y a pas de phase verrouillée : tous les artefacts sont de simples fichiers Markdown, modifiables à tout moment. Les artefacts sont le plan vivant, pas un contrat signé.

Constat pendant applyBoucle de retour
Une tâche est floue ou obsolèteModifier tasks.md à la main ou demander à l'assistant de le réviser, puis relancer /opsx:apply : il relit les fichiers actuels.
Un choix technique change (ex. cookie au lieu de localStorage)Mettre à jour design.md et la tâche concernée avant de continuer.
Le comportement attendu n'est plus le bonCorriger le delta de spec : il sera fusionné à l'archivage, il doit décrire ce qui est réellement livré.
Vous avez codé à la mainRéconcilier : soit la spec est périmée et vous la corrigez, soit le code a dérivé et vous le corrigez.
L'intention du change a fondamentalement changéDémarrer un nouveau change plutôt que rapiécer l'ancien.

/opsx:update (skill openspec-update-change dans ce dépôt, profil core) révise les artefacts de planification et les garde cohérents entre eux ; il ne modifie jamais le code. Ne le confondez pas avec la commande de terminal openspec update, qui régénère les fichiers d'intégration de l'assistant dans le projet. Après une révision, relancez /opsx:apply pour aligner le code.

Contrôler : vérifier n'est pas tester

Tests et lint du projet

Ils prouvent que le code s'exécute correctement (make test, make lint dans Playlab42). OpenSpec ne les remplace pas.

openspec validate --strict

Commande CLI qui contrôle la structure du change et des specs (format des deltas, cohérence des MODIFIED avec les specs principales). Elle ne lit pas votre code.

Dans Playlab42, le CLI est épinglé en 1.14.0 et s'exécute dans Docker, jamais sur l'hôte :

make npm CMD="exec -- openspec validate add-dark-mode --strict --no-interactive"
make openspec-validate   # tous les changes et specs

Hors Playlab42 : openspec validate add-dark-mode --strict.

/opsx:verify

Commande de l'assistant qui compare le code aux artefacts : complétude, justesse, cohérence. Rapport CRITICAL / WARNING / SUGGESTION, non bloquant.

profil expanded, pas core

Attention : /opsx:verify n'existe que si le workflow a été activé (openspec config profile, puis openspec update dans le projet). Dans Playlab42, seuls les six skills core sont générés : ne supposez pas verify installé. Sans lui, relisez le diff et les scénarios de spec vous-même, ou demandez à l'assistant une revue en langage naturel.

Approfondir : activer les commandes expanded 
openspec config profile   # choisir les workflows (verify, new, continue, ff...)
openspec update           # régénérer les fichiers de l'assistant dans le projet

Pas dans le dépôt Playlab42 : le guide du projet (docs/guides/openspec-workflow.md) interdit openspec init --force et openspec update directement dans le dépôt, pour préserver les alias et instructions existants. Le rafraîchissement des intégrations se fait par le mainteneur dans un projet temporaire isolé : suivez le guide plutôt que de recopier la procédure.

Le profil par défaut core fournit explore, propose, apply, update, sync et archive. Le profil étendu ajoute new, continue, ff, verify, bulk-archive et onboard.

Checklist avant d'archiver

  • Toutes les cases de tasks.md sont cochées.
  • Tests et lint du projet passent.
  • La validation stricte du change (make openspec-validate dans Playlab42) ne signale rien.
  • Les deltas de specs décrivent ce qui est réellement implémenté.
  • Le diff a été relu par un humain.
