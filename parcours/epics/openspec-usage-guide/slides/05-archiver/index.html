Étape 5 · Archiver

Archiver un change

Archiver ferme le change et fait entrer ses deltas dans les specs principales : c'est ce moment qui transforme « ce qu'on a proposé » en « ce que le système fait ».

Archiver n'est pas déployer. OpenSpec ne déploie rien : il déplace un dossier et fusionne des specs. En général, on archive quand le comportement décrit est réellement livré.

Politique de Playlab42 (règle du projet) : ne synchroniser ni archiver qu'après la livraison (merge, puis déploiement si applicable) et une décision explicite du mainteneur. Un code relu, ou même fusionné, ne suffit pas à lui seul.

Ce que fait l'archivage

  1. Contrôle : statut des artefacts et des tâches (avertit si des tâches restent à cocher).
  2. Synchronisation : fusion des deltas ADDED, MODIFIED, REMOVED dans openspec/specs/. Le contenu non mentionné par le delta est conservé.
  3. Déplacement : openspec/changes/add-dark-mode/ devient openspec/changes/archive/AAAA-MM-JJ-add-dark-mode/, avec tous les artefacts pour l'historique.
Section du deltaEffet sur la spec principale
## ADDED RequirementsExigence ajoutée
## MODIFIED RequirementsExigence existante remplacée
## REMOVED RequirementsExigence supprimée

Deux façons d'archiver

/opsx:archive (assistant)

Dans le chat de l'assistant :

/opsx:archive add-dark-mode

Dans Playlab42 : demander le skill openspec-archive-change par son nom (aucune commande slash n'est promise).

  • Vérifie les artefacts et les tâches.
  • Propose de synchroniser les deltas s'ils ne le sont pas encore.
  • Déplace le change vers archive/.
profil core

openspec archive (CLI)

Dans le terminal :

openspec archive add-dark-mode
openspec archive add-dark-mode --yes

Dans Playlab42, via Docker :

make npm CMD="exec -- openspec archive add-dark-mode --yes"
  • Valide le change (sauf --no-validate).
  • Demande confirmation ; --yes est requis pour un agent, la CI ou stdin fermé.
  • Fusionne les deltas puis déplace le dossier.
  • --skip-specs : change sans impact sur les specs (outillage, CI).

Le résultat visé est le même ; la différence est qui conduit l'opération : l'assistant, de façon interactive, ou la CLI, de façon déterministe et scriptable.

Synchroniser sans archiver : /opsx:sync

/opsx:sync (skill openspec-sync-specs dans ce dépôt, profil core) fusionne les deltas dans les specs principales mais laisse le change actif. Utile pour un change long ou si d'autres changes parallèles ont besoin des specs à jour. Pour un change rapide, archivez directement : l'archivage propose la synchronisation. Dans Playlab42, la politique d'archivage ci-dessus vaut aussi pour la synchronisation.

Plusieurs changes à la fois

/opsx:bulk-archive archive plusieurs changes terminés et traite les conflits de specs en regardant ce qui est réellement implémenté. Commande du profil expanded uniquement.

Approfondir : retirer une capacité entière

Si un change supprime la dernière exigence d'une capacité, l'archivage ne supprime son spec.md que si le fichier .openspec.yaml du change déclare retire_capabilities: true. Sans ce marqueur, l'archivage s'arrête avant de modifier quoi que ce soit.

# openspec/changes/retire-legacy/.openspec.yaml
schema: spec-driven
retire_capabilities: true

Fil rouge : archiver add-dark-mode (une fois livré)

make npm CMD="exec -- openspec validate add-dark-mode --strict --no-interactive"
make npm CMD="exec -- openspec archive add-dark-mode --yes"
make npm CMD="exec -- openspec list --specs"

Après archivage, la spec principale concernée (par exemple openspec/specs/ui/spec.md) contient les exigences du mode sombre et le dossier du change est sous openspec/changes/archive/.

Avant d'archiver

  • Le change est livré (merge, puis déploiement si applicable) et le mainteneur a décidé explicitement d'archiver.
  • Les tâches sont cochées et le code a été relu.
  • Les deltas décrivent le comportement réellement livré.
  • La validation stricte du change passe.
  • Si le workflow verify a été installé (profil expanded) : /opsx:verify a été passé.
