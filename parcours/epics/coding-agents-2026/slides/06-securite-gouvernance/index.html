🛡️ Sécurité et gouvernance

Un coding agent lit du contenu (code, issues, pages web, réponses d'outils) et agit avec vos droits (fichiers, terminal, jetons d'accès). Tout texte qu'il lit peut donc devenir une instruction : c'est l'injection de prompt. En 2025-2026, ce risque est passé de la théorie aux CVE.

Ce qui est arrivé

  • Nx « s1ngularity » (26-27 août 2025) : des versions piégées du paquet npm nx exécutaient un script à l'installation qui cherchait des secrets sur le disque et tentait d'utiliser les outils d'IA installés localement (Claude, Gemini) avec un prompt du type « You are a file-search agent… ».
  • Extension Amazon Q Developer pour VS Code 1.84.0 (juillet 2025, CVE-2025-8217) : un jeton GitHub mal cadré dans la chaîne de build a permis d'injecter du code destiné à appeler la CLI de l'agent. Il ne s'est pas exécuté à cause d'une erreur de syntaxe ; correctif en 1.85.0.
  • CVE d'août 2025 sur les agents eux-mêmes : Cursor (CVE-2025-54135, création d'une configuration MCP par injection de prompt indirecte menant à une exécution de code ; CVE-2025-54136, remplacement d'une configuration MCP déjà approuvée), Claude Code (CVE-2025-54795, contournement de la confirmation avant commande à partir de contenu non fiable), GitHub Copilot et Visual Studio (CVE-2025-53773, injection de commande permettant une exécution de code locale). Les avis de Cursor et de Claude Code indiquent des versions corrigées : gardez vos agents à jour.

Les paquets hallucinés (« slopsquatting »)

Spracklen et al. (USENIX Security 2025) ont généré 576 000 échantillons de code avec 16 modèles. Sur 2,23 millions de paquets suggérés, 19,7 % n'existaient pas (au moins 5,2 % pour les modèles commerciaux, 21,7 % pour les modèles open source), soit 205 474 noms inventés différents. Relancés dix fois, 43 % de ces noms réapparaissaient à chaque fois : un attaquant peut donc les prévoir et publier un paquet malveillant sous ce nom.

Les bonnes pratiques de l'ANSSI et du BSI

Dans leur publication commune AI Coding Assistants (octobre 2024), les agences française et allemande recommandent notamment :

  • de ne pas considérer ces outils comme un substitut à des développeurs expérimentés ;
  • de mener une analyse de risque avant leur introduction, y compris sur la confiance accordée aux fournisseurs ;
  • de faire relire et comprendre le code généré par les développeurs ;
  • de vérifier la plausibilité des bibliothèques inconnues ;
  • de renforcer l'assurance qualité (AppSec, DevSecOps) à proportion du gain de productivité.

En pratique : permissions minimales et confirmation des commandes sensibles, bac à sable ou machine dédiée pour l'autonomie, secrets hors de portée de l'agent, serveurs MCP et skills installés seulement depuis des sources connues, dépendances vérifiées, et relecture humaine avant intégration.

DateCe qui s'applique

Août 2025Règles pour les fournisseurs de modèles d'IA à usage général
2 août 2026Application générale, dont les règles de transparence
2 décembre 2027Systèmes à haut risque des domaines sensibles (reporté par l'AI Omnibus, entré en vigueur en juillet 2026)
2 août 2028Systèmes à haut risque intégrés à des produits réglementés

Les domaines « à haut risque » listés par la Commission (biométrie, infrastructures critiques, éducation, emploi, services essentiels, police, migration, justice) ne visent pas le développement logiciel en tant que tel. Pour une équipe de développement, l'enjeu immédiat est donc surtout la maîtrise de l'IA par les personnes, et la conformité du logiciel produit s'il relève lui-même d'un de ces domaines.
