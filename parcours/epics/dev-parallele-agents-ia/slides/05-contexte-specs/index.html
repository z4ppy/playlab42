📋 Donner le contexte aux agents : specs, pas duplication

Le problème du contexte

Chaque agent doit savoir :

  • ce qu'il doit faire : la tâche et ses critères de réussite ;
  • ce qu'il ne doit pas toucher : le périmètre ;
  • comment travailler : les conventions du projet.

La tentation est de recopier un fichier de configuration dans chaque worktree. Mauvaise idée : les copies divergent et personne ne sait laquelle fait foi.

L'approche spec-driven

Conventions et specs sont versionnées dans le dépôt. Comme un worktree extrait un commit, chaque agent les trouve dans son propre dossier… à condition qu'elles aient été commitées avant la création du worktree. 

mon-projet/                  # dépôt principal (branche main)
├── AGENTS.md                # conventions communes à tous les outils
├── CLAUDE.md                # contient « @AGENTS.md » pour Claude Code
└── specs/
    ├── auth-oauth.md        # spec de l'agent 1
    ├── api-notifications.md # spec de l'agent 2
    └── fix-tests.md         # spec de l'agent 3

mon-projet-agent-auth/       # worktree : contient aussi AGENTS.md et specs/
mon-projet-agent-api/
mon-projet-agent-tests/

📄 Les conventions : AGENTS.md et CLAUDE.md

AGENTS.md est un format ouvert d'instructions pour agents de code, géré depuis décembre 2025 par l'Agentic AI Foundation (Linux Foundation). Codex, Copilot, Cursor, Jules, Aider et beaucoup d'autres le lisent.

Claude Code charge automatiquement CLAUDE.md au début de chaque session. Il sait lire AGENTS.md lorsqu'aucun CLAUDE.md n'existe ; sinon, importez-le depuis CLAUDE.md avec la ligne @AGENTS.md. C'est ce que fait le dépôt Playlab42 : une seule source de conventions pour tous les outils. 

# AGENTS.md

## Stack
- Node.js 24, TypeScript, Express
- PostgreSQL, Prisma ORM
- Jest pour les tests

## Conventions
- Commits conventionnels (feat:, fix:, etc.)
- Tests obligatoires pour toute nouvelle fonction
- Pas de modification du schéma de base sans validation humaine

## Structure
- src/api/ : endpoints REST
- src/services/ : logique métier
- src/auth/ : authentification
- tests/ : tests unitaires et d'intégration

📝 Une spec par tâche

# Spec : authentification OAuth Google

## Objectif
Permettre aux utilisateurs de se connecter avec leur compte Google.

## Périmètre
- Fichiers à créer ou modifier : src/auth/oauth.ts, src/auth/google.ts
- Tests : tests/auth/oauth.test.ts

## Hors périmètre
- Ne PAS modifier les autres fournisseurs d'authentification
- Ne PAS toucher à src/api/**

## Critères de réussite
- [ ] Endpoint POST /auth/google fonctionnel
- [ ] Jeton JWT émis après authentification réussie
- [ ] Tests au vert

Lancer un agent avec sa spec

# 1. Commiter la spec sur main AVANT de créer le worktree
git add specs/auth-oauth.md && git commit -m "docs: spec OAuth Google"
git worktree add ../mon-projet-agent-auth -b feature/auth main

# 2a. Claude Code : @ inclut le contenu du fichier dans la demande
cd ../mon-projet-agent-auth
claude "Implémente @specs/auth-oauth.md"

# 2b. Aider : --read ajoute la spec en lecture seule
aider --read specs/auth-oauth.md
# puis, dans Aider : « Implémente cette spec »

Avec Claude Code, claude -w auth crée lui-même le worktree. Il part par défaut de la branche par défaut du dépôt : la spec doit donc y être commitée (et poussée si vous travaillez à plusieurs).

🛠️ Outils de spec-driven development

OutilWorkflowRemarque
OpenSpec /opsx:explore → /opsx:propose → /opsx:apply → /opsx:archive Workflow OPSX ; plus de 30 outils pris en charge. Les anciennes commandes /openspec:* sont « legacy ». Voir le parcours OpenSpec.
Spec Kit (GitHub) /speckit-constitution → -specify → -plan → -tasks → -implement Installation : uv tool install specify-cli puis specify init. La syntaxe exacte des commandes dépend de l'agent.
AGENTS.md Un fichier Markdown à la racine Format ouvert, lu par la plupart des agents.

Pourquoi cette approche est meilleure

ApprocheAvantagesInconvénients
Configuration copiée par worktreeSimple au débutDivergence, maintenance, aucune vue globale
Specs versionnéesSource unique, historique, réutilisable par tous les outilsUn peu plus de préparation

Les specs deviennent une documentation vivante. Quand une feature est terminée, sa spec explique ce qui a été fait et pourquoi.
