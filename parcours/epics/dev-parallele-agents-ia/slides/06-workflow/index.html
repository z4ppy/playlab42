🔄 Workflow complet : de la préparation à l'intégration

Préparer → Lancer → Surveiller → Relire → Intégrer → Nettoyer.

1. Préparer

Découper la tâche en sous-tâches qui touchent des fichiers disjoints :

Tâche globale : « Ajouter un système de notifications »

Agent 1 : service de notifications   (src/services/notifications/*)
Agent 2 : endpoints API              (src/api/notifications/*)
Agent 3 : composants d'interface     (src/components/notifications/*)

Si les sous-tâches dépendent les unes des autres, écrivez d'abord le contrat commun (types, interfaces, format des messages) et commitez-le. Puis écrivez les specs, commitez-les et créez les worktrees : 

git add specs/ src/types/notifications.ts
git commit -m "docs: specs et contrat du système de notifications"

git worktree add ../notif-backend  -b feature/notif-backend  main
git worktree add ../notif-api      -b feature/notif-api      main
git worktree add ../notif-frontend -b feature/notif-frontend main

2. Lancer

tmux new-session -s agents
# Un panneau par worktree (Ctrl-A | ou Ctrl-A - avec la configuration vue plus haut)
cd ../notif-backend  && claude "Implémente @specs/notif-backend.md"
cd ../notif-api      && claude "Implémente @specs/notif-api.md"
cd ../notif-frontend && claude "Implémente @specs/notif-frontend.md"

Variante sans terminal à surveiller : confiez chaque spec à un agent cloud (claude --cloud "Implémente la spec specs/notif-api.md", issue assignée à Copilot…). Les étapes suivantes restent les mêmes.

3. Surveiller

Ne micro-managez pas, mais passez régulièrement (toutes les 15 à 30 minutes, par exemple) :

  • Un agent attend-il une permission ou une réponse ?
  • Un agent part-il dans une mauvaise direction ou sort-il de son périmètre ?
  • La même erreur revient-elle en boucle ? Arrêtez plutôt que de laisser « réessayer ».

Entre deux passages, commencez la relecture du premier agent qui a terminé.

4. Relire

C'est le goulot d'étranglement. Lancer des agents est rapide ; relire sérieusement chacun de leurs diffs prend du temps. Prévoyez-le dès le découpage.

Pour chaque branche :

  1. Lire le diff : git diff main...feature/notif-backend
  2. Vérifier le périmètre : aucun fichier hors spec, aucun test supprimé ou désactivé.
  3. Relancer soi-même les tests et le lint, sans se fier au résumé de l'agent.
  4. Vérifier la logique métier et la sécurité : entrées, secrets, dépendances ajoutées.
  5. Demander des corrections, ou jeter et relancer avec une spec plus précise.

Une partie du travail peut être à reprendre, voire à refaire. Si une même tâche échoue deux fois, réexaminez la spec et le découpage avant de relancer.

5. Intégrer

La voie la plus sûre : une pull request par agent, qui passe par la CI et une revue.

cd ../notif-backend
git push -u origin feature/notif-backend
gh pr create --base main --fill

Ordre recommandé : contrat et types, puis services, API, interface, et enfin tests d'intégration. Après chaque fusion, mettez les branches suivantes à jour depuis main et relancez leurs tests.

Sans plateforme de revue, l'équivalent local depuis le worktree principal :

git switch main
git merge --no-ff feature/notif-backend
git merge --no-ff feature/notif-api
git merge --no-ff feature/notif-frontend

En cas de conflit, deux branches ont modifié les mêmes lignes : le découpage n'était pas complètement disjoint. Résolvez, puis notez-le pour mieux découper la prochaine fois. git config rerere.enabled true fait mémoriser à Git les résolutions de conflits pour les rejouer.

6. Nettoyer

git worktree remove ../notif-backend
git worktree remove ../notif-api
git worktree remove ../notif-frontend
git worktree prune

# -d refuse de supprimer une branche non fusionnée : c'est voulu
git branch -d feature/notif-backend feature/notif-api feature/notif-frontend

Après une fusion par « squash » sur la plateforme, Git local ne reconnaît pas la branche comme fusionnée : vérifiez que la PR est bien fusionnée avant de forcer la suppression avec -D.
