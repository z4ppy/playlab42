☁️ Agents en arrière-plan dans le cloud

Les principaux éditeurs proposent d'exécuter un agent hors de votre machine. Chaque tâche obtient sa propre machine virtuelle ou son conteneur, clone le dépôt, travaille sur une branche et vous rend une pull request. C'est le même principe que « un worktree par agent », poussé jusqu'à « une machine par agent ».

Panorama au 8 novembre 2026

OffreOù tourne l'agentComment le lancerRésultat
Claude Code on the web (Anthropic) VM isolée gérée par Anthropic claude.ai/code, ou claude --cloud "…" depuis le terminal Branche poussée, PR créée depuis l'interface
Codex cloud (OpenAI) Un espace de travail par tâche, qui continue même ordinateur en veille Interface Codex Commit ou pull request quand vous le décidez
Copilot cloud agent (GitHub) Environnement basé sur GitHub Actions Assigner une issue à Copilot, ou /delegate depuis Copilot CLI Pull request en brouillon, revue demandée
Cursor Cloud Agents VM cloud avec environnement de développement complet Cursor PR prête à relire, avec démonstration des changements
Jules (Google) VM cloud jules.google, ou label jules sur une issue Plan à valider, puis PR

Noms et fonctions bougent vite : l'agent de Copilot s'appelait « Copilot coding agent » jusqu'en avril 2026, et les Cloud Agents de Cursor s'appelaient « Background Agents ». Vérifiez la documentation de l'éditeur avant une démonstration.

Lancer plusieurs tâches depuis le terminal

Avec Claude Code, chaque commande --cloud crée une session indépendante ; elles tournent simultanément :

claude --cloud "Implémente la spec specs/notif-backend.md"
claude --cloud "Implémente la spec specs/notif-api.md"

# Récupérer une session cloud dans le terminal pour la terminer en local
claude --teleport

Le passage se fait du cloud vers le terminal ; on ne pousse pas une session de terminal existante vers le cloud depuis la CLI. L'ancienne option --remote reste acceptée mais est dépréciée.

Ce que le cloud règle… et ce qu'il ne règle pas

RégléToujours à votre charge
Conflits de ports, de base de données et de RAM sur votre posteDécrire l'environnement : dépendances, script d'installation, accès réseau
Votre machine reste libre ; le travail continue pendant que vous êtes absentLa revue de chaque PR et l'ordre d'intégration
Isolation forte entre tâchesLe coût : chaque tâche consomme quotas, crédits ou minutes de calcul
Traçabilité : une branche et une PR par tâcheLes secrets : ne donnez que les accès nécessaires à la tâche

Une issue est une entrée non fiable. Un agent qui lit une issue, un commentaire ou une page web peut y trouver des instructions écrites par un tiers (injection de prompt). Limitez ses permissions et son accès réseau, et relisez la PR comme celle d'un contributeur inconnu.

Et en local, un bac à sable ?

Si vous voulez l'isolation sans le cloud, Docker Sandboxes exécute un agent dans un environnement isolé sur votre machine, par exemple sbx run claude ~/mon-projet. Lisez sa documentation pour savoir quels fichiers, réseaux et permissions l'agent y reçoit.
