🔀 La solution : Git Worktree

Le principe

git worktree (apparu dans Git 2.5, en juillet 2015, d'abord marqué expérimental) attache plusieurs répertoires de travail à un même dépôt. Chaque worktree a ses fichiers, son index et son HEAD ; l'historique et les branches sont partagés. Un commit fait dans un worktree est immédiatement visible depuis les autres.

Ce qui est isolé, ce qui est partagé

Propre à chaque worktreePartagé par tous les worktrees
Fichiers extraits, y compris non suivisObjets Git (historique)
HEAD et branche couranteBranches et tags (refs/)
Index (staging area)Configuration du dépôt et hooks
node_modules, builds, caches locauxLe stash (refs/stash)

Deux règles à connaître.

  • Une branche ne peut être extraite que dans un seul worktree. Git refuse la seconde extraction (message du type fatal: 'feature/auth' is already used by worktree at …, selon la version). L'option --force contourne ce garde-fou : ne l'utilisez pas pour des agents.
  • Un fichier non commité dans votre worktree n'existe pas dans les autres. Commitez specs et conventions avant de créer les worktrees des agents.

Côté disque, un worktree ne recopie pas l'historique : son .git est un fichier d'une ligne qui pointe vers le dépôt principal. En revanche, les fichiers extraits, les dépendances installées et les sorties de build sont dupliqués dans chaque worktree.

Mise en place

Option 1 : depuis un dépôt existant (le plus simple)

cd mon-projet
git switch main && git pull

# Un worktree et une branche par agent, à côté du dépôt
git worktree add ../mon-projet-agent-auth -b feature/auth main
git worktree add ../mon-projet-agent-api  -b feature/api  main
git worktree add ../mon-projet-agent-tests -b fix/tests   main

Option 2 : dépôt « bare » et un dossier par worktree

Cette organisation range tous les worktrees, y compris main, au même niveau.

mkdir mon-projet && cd mon-projet
git clone --bare git@github.com:user/projet.git .bare
echo "gitdir: ./.bare" > .git

# Un clone bare ne configure pas les branches distantes : on les ajoute
git config remote.origin.fetch "+refs/heads/*:refs/remotes/origin/*"
git fetch origin

# Extraire la branche locale main (et non origin/main, qui donnerait un HEAD détaché)
git worktree add main main
git -C main branch --set-upstream-to=origin/main

Commandes essentielles

git worktree add <chemin> -b <nouvelle-branche> <base>  # créer
git worktree list                                       # lister
git worktree remove <chemin>                            # supprimer (refuse si non propre)
git worktree prune                                      # nettoyer les références orphelines

git worktree remove refuse un worktree qui contient des modifications ou des fichiers non suivis. C'est une protection : vérifiez ce qui reste avant d'ajouter --force.

Les outils le font aussi pour vous

En 2026, les principaux agents savent créer leurs worktrees eux-mêmes :

OutilUsageCe qui se passe
Claude Code claude -w feature-auth Worktree dans .claude/worktrees/feature-auth/, branche worktree-feature-auth. À la sortie, Claude propose de garder ou supprimer le worktree.
Cursor /worktree, /best-of-n L'agent travaille dans un checkout isolé ; /best-of-n lance la même tâche sur plusieurs modèles, un worktree chacun.
Codex (application) Mode « Worktree » sous la zone de saisie Plusieurs conversations sur le même projet sans interférer.

Comprendre la commande Git reste utile : c'est elle qu'il faut savoir inspecter, nettoyer et dépanner quand un outil laisse des worktrees derrière lui. Avec Claude Code, un fichier .worktreeinclude liste les fichiers ignorés par Git (comme .env) à copier dans chaque nouveau worktree.

🐳 Et les services (base de données, Redis…) ?

Les worktrees isolent le code, pas les services. Docker Compose nomme par défaut un projet d'après son dossier (sauf si le fichier fixe un name:) : deux worktrees obtiennent donc des conteneurs distincts, mais les ports publiés sur la machine entrent en collision. Paramétrez-les : 

# docker-compose.yml
services:
  db:
    image: postgres:17
    ports:
      - "${DB_PORT:-5432}:5432"
  redis:
    image: redis:7-alpine
    ports:
      - "${REDIS_PORT:-6379}:6379"
# mon-projet-agent-auth/.env
DB_PORT=5410
REDIS_PORT=6310

# mon-projet-agent-api/.env
DB_PORT=5420
REDIS_PORT=6320

Une convention simple : PORT = BASE + (INDEX_AGENT × 10). Ce dépôt Playlab42 applique le même principe : chaque worktree reçoit un nom de projet Docker et un port uniques (make info affiche l'instance courante).
