Méthodes : agents, OpenSpec et skills

Un agent IA travaille mieux avec un contexte écrit. Dans PlayLab42, ce contexte tient en trois couches : AGENTS.md, OpenSpec (OPSX) et les skills.

Les trois couches

AGENTS.md

Source commune des conventions : Docker-first, stack, tests, règles de contribution. Les agents le lisent avant d'agir.

OpenSpec / OPSX

Un change contient proposal.md, specs/, design.md et tasks.md (schéma spec-driven).

Skills

Des consignes de tâche réutilisables : six skills openspec-* et cinq skills métier playlab-*.

OPSX 1.14 : le profil core

Le dépôt est généré avec OpenSpec 1.14.0, profil core : six actions. Le CLI est une dépendance locale épinglée, exécutée avec Node 26 dans Docker ; on ne l'installe pas globalement.

ActionSkill du dépôtCommande générique si votre client la fournit
Exploreropenspec-explore/opsx:explore
Proposeropenspec-propose/opsx:propose
Implémenteropenspec-apply-change/opsx:apply
Réviseropenspec-update-change/opsx:update
Synchroniseropenspec-sync-specs/opsx:sync
Archiveropenspec-archive-change/opsx:archive

Ici, la source est le skill. La colonne de droite est la commande générique d'un assistant : le dépôt est livré en « skills-only », donc aucune commande slash n'est garantie. Demandez simplement « utilise le skill openspec-propose ». Les trois alias locaux /openspec:proposal, /openspec:apply et /openspec:archive restent des compatibilités locales, pas le workflow global actuel.

Où vivent les skills

  • Les corps sont versionnés uniquement dans .github/skills/ (canonique).
  • .claude/skills est un lien symbolique vers ce dossier : pas de seconde copie.
  • Le lien ne crée aucune commande slash ; les skills restent distincts du CLI openspec.

À ne pas faire dans ce dépôt : openspec init --force et openspec update directement dans le worktree. Ils peuvent supprimer les alias, openspec/AGENTS.md et des marqueurs historiques. Le rafraîchissement des skills est une opération de mainteneur, dans un projet temporaire isolé, puis revue du diff.

Livrer sans simuler

Une demande d'implémentation explicite autorise son périmètre, rien de plus. On ne fabrique ni revue, ni CI verte, ni merge, ni déploiement. L'archivage attend la livraison (merge et déploiement si applicable) et une décision explicite d'un humain.

Mini-exercice

Votre agent a terminé le code d'un change. Peut-il l'archiver tout de suite ? Quelle commande lancez-vous pour valider les specs ?

Correction

Non : l'archivage attend la livraison et une décision explicite. Validation dans Docker : make openspec-validate, qui lance openspec validate --all --strict --no-interactive avec le CLI épinglé.
