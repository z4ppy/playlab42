Qualité et CI

À chaque pull request vers main, GitHub Actions rejoue les contrôles. La publication réutilise cette même CI ; l'audit de sécurité reste un workflow séparé.

CI : huit contrôles complémentaires

Les jobs utilisent Node 26 et npm ci. Browser attend l'archive du job Build :

  • Lint : npm run lint, erreurs et avertissements bloquants.
  • Security lint : plugins verrouillés et règles JS ciblées ; les heuristiques consultatives restent séparées.
  • Tests : npm run test:coverage, seuils ciblés sur le déterminisme et la livraison ; upload Codecov non bloquant.
  • Dépendances : npm run audit:dependencies, seuil modéré ; une panne d'audit bloque aussi.
  • TypeScript : npm run typecheck ; la transpilation est réalisée dans Build.
  • OpenSpec : npm run openspec:validate, strictement sur specs et changes actifs.
  • Build : npm run build (TypeScript, runtime, catalogues, guides et dossier public site/).
  • Browser : Playwright sur l'archive construite, avant publication.

Lire la politique qualité et le plan de progression : conception, erreurs, tests et revue.

Navigateur : tester ce qui sera publié

Le job « Chromium interactions » installe Chromium, extrait l'archive github-pages et lance npm run test:e2e avec PLAYWRIGHT_PREBUILT=1 : le serveur sert site/ sans reconstruire les catalogues. En cas d'échec, il publie l'artefact ui-e2e-failure (rapport et traces, 14 jours).

Ne mélangez pas trois idées : les tests Jest vérifient la logique, les tests navigateur vérifient l'interface réelle, et openspec validate vérifie seulement la structure des specs. Aucun ne remplace les autres. Le job OpenSpec est désormais intégré à la CI ; vous pouvez également l'exécuter dans Docker avec make openspec-validate.

Actions épinglées par SHA, images par digest et scanners vérifiés avant exécution. Les bases CVE et paquets OS évoluent encore. Le lint TypeScript attend un parser compatible avec TS 7 ; le contrôle de types reste actif, mais n'est pas du lint.

Ce que ces workflows ne garantissent pas

Les fichiers décrivent ce qui s'exécute. Savoir quels checks sont obligatoires avant un merge dépend des réglages GitHub. Une protection classique a été activée et relue via l'API le 3 octobre 2026 : PR, neuf checks natifs et discussions résolues, même pour l'admin. Aucun force-push ni suppression. Avec un seul mainteneur, aucune approbation externe n'est encore obligatoire ; une revue indépendante reste à organiser. Les noms requis ont été ajustés aux résultats natifs de la PR #135 ; le garde-fou de publication et la protection de branche sont deux mécanismes distincts.

Lancer les mêmes contrôles en local (Docker)

make info          # instance, port, URL du worktree
make lint
make typecheck
make test
make test-e2e
make openspec-validate

Aucune installation sur votre machine : tout passe par Docker. Les secrets et jetons ne s'affichent jamais, ni dans les logs ni dans les slides.

hello-usine, étape qualité

La contribution hello-usine (imaginaire) arrive en PR. Avant de la demander en revue, vérifiez :

  • le test du moteur ou de l'outil passe dans Docker ;
  • lint et build passent ;
  • aucun secret n'a été ajouté ;
  • vous n'affirmez pas « CI verte » sans avoir lu les résultats réels.
Mini-question : ESLint Security signale un problème, la PR est-elle bloquée ?

Pas par ce job : il affiche un avertissement et continue. Une règle de branche éventuelle reste à vérifier dans les réglages GitHub.
