Qualité et CI

À chaque pull request, y compris sur une branche de lot empilé, GitHub Actions rejoue les contrôles. La publication réutilise cette même CI ; l'audit de sécurité reste un workflow séparé.

CI : dix contrôles complémentaires

Les jobs utilisent Node 26 et npm ci. Browser attend l'archive du job Build :

  • Lint : npm run lint, ESLint JS/scripts HTML puis Biome TS, erreurs et avertissements bloquants.
  • Security lint : plugins verrouillés et règles JS/scripts HTML ciblées ; les heuristiques consultatives restent séparées.
  • Tests : npm run test:coverage, seuils ciblés sur le déterminisme et la livraison ; upload Codecov non bloquant.
  • Dépendances : npm run audit:dependencies, seuil modéré ; une panne d'audit bloque aussi.
  • TypeScript : npm run typecheck ; la transpilation est réalisée dans Build.
  • OpenSpec : npm run openspec:validate, strictement sur specs et changes actifs.
  • Code quality : npm run quality:report, budgets absolus de production ; dépassement bloquant pour Build.
  • Trivy : scan partagé, HIGH/CRITICAL bloquants pour Build.
  • Build : npm run build (TypeScript, runtime, catalogues, guides et dossier public site/).
  • Browser : Playwright sur l'archive construite, avant publication.

Lire la politique qualité et le plan de progression : conception, erreurs, tests et revue.

Qualité : vérifier des contrats, pas seulement un score

La production JS et les scripts HTML ont un seuil ESLint de complexité de 10 par fonction et des seuils de couverture ciblés. Une permission refusée n'est pas un fichier absent ; un cache corrompu ou daté dans le futur n'est pas un cache valide. Les catalogues JSON sont remplacés atomiquement, après validation : une erreur conserve le précédent.

Ces garanties ne sont pas une certification globale : pas de seuil universel, ni de transaction couvrant tous les fichiers, ni de garantie de durabilité après coupure électrique. Tester les erreurs et les invariants reste plus utile que découper du code pour verdir un score.

Navigateur : tester ce qui sera publié

Le job « Chromium interactions » installe Chromium, Firefox et WebKit, extrait l'archive github-pages et lance npm run test:e2e avec PLAYWRIGHT_PREBUILT=1 : le serveur sert site/ sans reconstruire les catalogues. En cas d'échec, il publie l'artefact ui-e2e-failure (rapport et traces, 14 jours).

Dans ce même check requis, un smoke ciblé vérifie navigation/jeu au clavier, thème/pseudonyme persistant et récupération après une erreur JSON sur les trois moteurs. La suite complète reste Chromium : ce n'est pas une certification multi-navigateur de tous les jeux, de l'audio ou de la 3D. Les neuf noms de checks requis restent inchangés.

Ne mélangez pas trois idées : les tests Jest vérifient la logique, les tests navigateur vérifient l'interface réelle, et openspec validate vérifie seulement la structure des specs. Aucun ne remplace les autres. Le job OpenSpec est désormais intégré à la CI ; vous pouvez également l'exécuter dans Docker avec make openspec-validate.

Actions épinglées par SHA, images par digest et scanners vérifiés avant exécution. Les bases CVE et paquets OS évoluent encore. Biome fournit le lint des sources .ts sans forcer un parser incompatible avec TS 7. Le contrôle de types reste distinct ; les plugins de sécurité ESLint ne s'appliquent pas à TS. Le lint HTML vise les scripts, pas le markup : un test interdit les attributs événementiels au profit de listeners lintés.

Ce que ces workflows ne garantissent pas

Les fichiers décrivent ce qui s'exécute. Savoir quels checks sont obligatoires avant un merge dépend des réglages GitHub. Une protection classique a été activée et relue via l'API le 3 octobre 2026 : PR, neuf checks natifs et discussions résolues, même pour l'admin. Aucun force-push ni suppression. Avec un seul mainteneur, aucune approbation externe n'est encore obligatoire ; une revue indépendante reste à organiser. Les noms requis ont été ajustés aux résultats natifs de la PR #135 ; le garde-fou de publication et la protection de branche sont deux mécanismes distincts.

Les lots 3 à 5 sont intégrés à main et publiés via la PR #144. La PR de revue issue de fix/review-software-factory fait de Build, déjà requis, un gate exigeant le succès de Security lint et de Trivy HIGH/CRITICAL via un workflow réutilisable partagé ; un gate ignoré ne doit pas autoriser la suite. Sa validation native est datée dans le guide de l'usine ; ce n'est pas une livraison. Les correctifs ont depuis été intégrés à main et publiés via la PR #145 : une preuve de publication distincte est référencée dans ce guide. Les neuf checks GitHub actuellement requis ne sont pas modifiés.

Tests avant refactoring

Commencez par un comportement observable : refus sans mutation, erreur visible, chargements concurrents ou reprise d'un moteur après sauvegarde JSON. Exécutez le test sur le code initial, puis corrigez le défaut reproduit. Une fonction déjà conforme n'a pas besoin d'être réécrite.

La couverture guide les priorités ; une couverture élevée ne prouve pas la qualité des assertions. Les seuils s'ajoutent par module après mesure, sans abaisser les protections existantes. Les tests Jest et les interactions d'une vraie archive dans Chromium apportent des preuves différentes.

Le socle tests-first est livré via la PR #147 : portail, moteurs et Simulation disposent de scénarios et de seuils ciblés. La suite quality/core-refactors est livrée via la PR #148 : contrats communs, seed explicite, mutualisation du RNG et séparation des responsabilités. Extraire du code doit conserver son instrumentation ; ce n'est pas un moyen de gonfler la couverture.

La PR #149 a livré quality:report dans la CI : duplication locale jscpd, complexité cyclomatique JS/HTML et cognitive TS. Comparez les compteurs à périmètre constant ; gardez production, tests et supports pédagogiques distincts. Un clone détecté n'est pas automatiquement un défaut à supprimer. La PR #150 a livré la correction des six hotspots de production au-dessus de 20 dans quality/rendering-audio, après caractérisation des rendus et contrats audio. La PR #151 a livré la simplification de fabrication et vérification d'archive dans quality/artifact-pipeline, après tests de comportement. La suite quality/application-contracts caractérise les orchestrations et protège les contrats applicatifs en scopes parallèles ; elle n'est pas encore livrée.

« Parfait » n'est pas un critère vérifiable. Préférez des responsabilités compréhensibles, des erreurs et courses caractérisées, des budgets explicites et des limites honnêtes. Un zéro Jest ne prouve pas l'absence de tests navigateur ; un clone détecté ne justifie pas automatiquement une abstraction. Chaque extraction reste instrumentée et protégée.

Lancer les mêmes contrôles en local (Docker)

make info          # instance, port, URL du worktree
make lint
make typecheck
make test
make test-e2e
make openspec-validate

Aucune installation sur votre machine : tout passe par Docker. Les secrets et jetons ne s'affichent jamais, ni dans les logs ni dans les slides.

hello-usine, étape qualité

La contribution hello-usine (imaginaire) arrive en PR. Avant de la demander en revue, vérifiez :

  • le test du moteur ou de l'outil passe dans Docker ;
  • lint et build passent ;
  • aucun secret n'a été ajouté ;
  • vous n'affirmez pas « CI verte » sans avoir lu les résultats réels.
Mini-question : ESLint Security signale un problème, la PR est-elle bloquée ?

Une règle du gate bloquant échoue réellement et empêche la publication. Les heuristiques de la commande advisory restent consultatives et ne prouvent pas une vulnérabilité. La protection de branche est un mécanisme distinct.
