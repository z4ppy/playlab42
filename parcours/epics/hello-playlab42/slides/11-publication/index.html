Publication

Dernière étape : publier ce qui a été vérifié. deploy.yml appelle la CI, attend ses contrôles et publie la même archive sur GitHub Pages. L'application reste statique.

Quand se déclenche-t-il ?

  • À chaque push sur main (donc après un merge de PR).
  • Manuellement (workflow_dispatch) depuis Actions, sur main uniquement ; une autre référence fait échouer le contrôle.
  • Seul le job de publication reçoit écriture Pages et id-token. Un seul déploiement à la fois (concurrency: pages, sans annulation du déploiement en cours).

Le DAG : validation, publication, contrôle

  1. check-ref : refuse de publier une autre référence que main.
  2. validate : appelle ci.yml pour le même commit. Lint, tests, types et OpenSpec doivent réussir.
  3. Build → Browser : prépare site/, archive github-pages, puis teste l'archive extraite sans reconstruction.
  4. deploy (needs: validate) : publie cette même archive après le succès de toute la CI.
  5. smoke : compare le SHA publié au commit du run et vérifie dix ressources HTTP, dont build-manifest.json (identité et empreintes lockfile/snapshot). Ces dix ressources ne sont pas les neuf checks GitHub requis.

Que fait npm run build ?

  1. build:ts : transpile les contenus TypeScript vers dist/.
  2. build:runtime : génère les bibliothèques navigateur (Tone, VexFlow, MathJax…) dans assets/vendor/ depuis les versions épinglées dans package.json et vérifiées par scripts/runtime-vendors.json.
  3. build:catalogue : lit les manifests tool.json et game.json, écrit data/catalogue.json.
  4. build:parcours : lit epic.json et slide.json, écrit data/parcours.json.
  5. build:bookmarks : écrit data/bookmarks.json.
  6. build:guides : transforme les Markdown de docs/ en pages HTML dans docs/site/.
  7. build:site : copie les ressources publiques dans site/, avec build-info.json (version et commit CI).
  8. build:provenance : ajoute SBOM npm de fabrication et manifeste des fichiers publics avec SHA-256.

Les fichiers générés (dist/, catalogues, assets/vendor/, docs/site/, site/) sont ignorés par Git : ne les commitez pas, la CI les recrée à chaque fois.

Ce qui n'est PAS automatique

Seul le dossier public est archivé : pas de node_modules/, tests, caches ou configuration d'agents. Le build utilise le snapshot OG revu ; la collecte est réservée à refresh:bookmarks. La CI compare deux fabrications à epoch identique et vérifie l'archive avant le navigateur. Le workflow n'archive pas les changes OpenSpec et ne crée pas de release. L'archivage demande une livraison effective puis une décision explicite du mainteneur (openspec-archive-change). Et aucun skill ne fusionne une PR à votre place.

Le smoke test effectue au plus cinq tentatives pour la propagation Pages. Son échec rend le run rouge, mais le site est déjà publié : aucun rollback automatique. build-info.json identifie le commit ; ce n'est pas une attestation signée.

Les lots 3 à 5 sont intégrés à main et publiés via la PR #144 le 3 octobre 2026. Le workflow de monitoring est versionné, mais cela ne prouve pas un run cron exécuté. Les correctifs de revue du worktree restent distincts de cette livraison : ni intégrés à main, ni validés par une CI native.

Tester le résultat chez vous (Docker)

make info          # nom d'instance, port, URL
make up            # démarre le conteneur du worktree
make npm CMD="run build:local"
make serve         # sert sur le port affiché par make info

Chaque worktree Git a son projet Docker et son port (plage 5200-5299, calculé depuis le nom du dossier) : plusieurs branches peuvent tourner en parallèle sans conflit. Pour reconstruire comme le fait le déploiement, le mode local prépare aussi site/, mais omet l'enrichissement du snapshot.

Lire le runbook : reproductibilité, inventaire, monitoring et reprise. check:recovery teste une vraie archive localement ; aucune reprise de production n'est implicite.

hello-usine : le trajet complet

  1. Spec OpenSpec de l'outil, approuvée par vous.
  2. Skill playlab-ui, kit scaffold, implémentation.
  3. Tests, lint et build dans Docker.
  4. PR : checks CI et audit de sécurité.
  5. Merge décidé par un humain, puis deploy.yml.
  6. L'outil apparaît dans le catalogue du site publié.
  7. Contrôle du commit publié, puis décision explicite de synchronisation/archivage.
Mini-question : j'ai ajouté un manifeste, quand apparaît-il dans le portail ?

Après le build qui régénère les catalogues JSON : en local avec make build-catalogue, en ligne après le déploiement sur main.

Sources : deploy.yml, package.json, runtime-vendors.json, skill playlab-release.
