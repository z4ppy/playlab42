Comprendre la plateforme

L'architecture

PlayLab42 est une plateforme 100 % statique : des fichiers HTML, CSS et JavaScript servis tels quels. Aucun backend, aucun WebSocket. Cette slide pose la carte du terrain ; la suite montre l'« usine » qui produit ces fichiers.

Vue d'ensemble : trois couches

1. Le portail

index.html, app.js et app/. Il lit des catalogues JSON (outils, jeux, parcours) et affiche chaque module dans une iframe.

2. Les modules

tools/ (outils), games/ (jeux) et parcours/ (slides). Chacun vit dans son dossier avec son manifeste JSON.

3. Les bibliothèques

lib/ : GameKit (dialogue portail ↔ jeu), thèmes, données locales dans le navigateur, aléa à graine (seeded-random.js).

Un jeu = trois pièces séparées

  1. Moteur : règles en JavaScript pur, déterministe (même graine + mêmes actions = même partie). Il tourne dans le navigateur et dans Node pour les tests.
  2. Client : l'interface HTML qui affiche l'état et envoie les actions.
  3. Bot : un joueur automatique du jeu. Il ne voit que la vue du joueur et les actions légales.

Attention au vocabulaire : un bot de jeu est du code du produit. Il n'a rien à voir avec un agent de code (Copilot, Claude…) qui aide à écrire le dépôt. Ni l'un ni l'autre n'est un backend autonome.

Ce qui n'existe pas (volontairement)

  • Pas de serveur applicatif ni de base de données.
  • Pas de WebSocket : la compatibilité Node des moteurs prépare l'avenir, elle n'en crée pas un.
  • TypeScript est optionnel : il est vérifié ou compilé au build, jamais requis pour écrire un module.

Mini-question : où tourne la logique d'un jeu ?

Dans le navigateur, via le moteur JavaScript du jeu. Aucun serveur n'est sollicité ; Node ne sert qu'aux tests et au build.
