Specs et skills

Avant de coder, on écrit ce qu'on veut (OpenSpec). Pour guider l'agent de code, on lui donne des instructions versionnées (skills). Ce sont des fichiers Markdown : aucun agent autonome ni backend n'est ajouté.

Fil rouge : hello-usine

Imaginons un outil hello-usine (illustratif, non créé) qui affiche un message. Il traverse l'usine de la spec jusqu'à GitHub Pages.

1. OpenSpec : la spec d'abord

Le schéma spec-driven est choisi dans openspec/config.yaml. Un change contient quatre artefacts :

  1. proposal.md : pourquoi et quoi (impact, exclusions).
  2. specs/<capability>/spec.md : exigences avec SHALL/MUST et au moins un #### Scenario:.
  3. design.md : décisions techniques.
  4. tasks.md : tâches à cocher, uniquement une fois réalisées et vérifiées.

2. Les six skills OpenSpec (profil core)

ActionSkill (source canonique)
Explorer sans implémenteropenspec-explore
Préparer un changeopenspec-propose
Implémenteropenspec-apply-change
Réviser les artefactsopenspec-update-change
Synchroniser les specsopenspec-sync-specs
Archiveropenspec-archive-change

Ils ont été générés par le CLI OpenSpec 1.14.0 (generatedBy: "1.14.0"), en livraison « skills seulement ». Les commandes /opsx:* ne sont pas installées automatiquement : demandez le skill par son nom.

3. Les cinq skills métier Playlab42

playlab-ui

Portail, outils, clients, interactions accessibles.

playlab-create-game

Moteur, règles, bots, manifeste et client d'un jeu.

playlab-create-epic

Parcours, manifests, slides et build.

playlab-release

Branche, validations, PR ; jamais de merge automatique.

playlab-review

Revue de conception, contrats, tests et risques ; preuves et limites explicites.

Les corps vivent uniquement dans .github/skills/. Le lien .claude/skills → ../.github/skills expose les mêmes fichiers à Claude : pas de seconde copie.

Garde-fous à connaître

  • CLI OpenSpec local épinglé en 1.14.0, exécuté dans Docker (Node 26), jamais sur le host.
  • Ne pas lancer openspec init --force ni openspec update dans ce dépôt : migration destructive possible.
  • Une proposal générée n'est pas une approbation de livraison.
  • Ne pas archiver avant la livraison et une décision explicite.
  • La validation OpenSpec vérifie la structure des specs, pas le code.
